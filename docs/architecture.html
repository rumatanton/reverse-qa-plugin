Claude Code plugin · open source, MIT

reverse-qa

Give it an app with no documentation. It documents the architecture, security, roles and workflows (every claim cites a file and line), writes requirements, user stories and Xray test cases, builds and runs a Playwright framework with performance, security and upgrade checks, and turns confirmed defects into Jira-ready bug reports.

It is not tied to a stack or to one app. How it works has the diagrams; the quick start puts your own app under it.

  • init-target looks at a source folder, says what the app is and why, prints what works for it today, writes its target.yaml, and checks the prerequisites.
  • crawl-app walks the running app as every role: GET only, inside the app, skipping links that look destructive. An OpenAPI spec lists an API's endpoints. scan-repo merges both with the source scan and flags routes in the code that neither reached.
  • First crawl of a real web app, a PHP shop: 29 of the 33 pages the PHP parser knows, found from the running app alone (the four missed are the logout page, which it skips on purpose, and three payment pages only a form post reaches). It left 12 destructive links alone, among them 11 "Delete" links with harmless-looking addresses, and recorded 17 page-and-role cases where the app logged a server error behind a redirect: the same defect class the parser and the tests found, seen with no parser.
  • Checked end to end on a second app, a small Node JSON API with a spec and a token login that the plugin keeps as a test fixture: from its source folder to 26 passing tests, with no browser and nothing PHP.

How a run works

  1. Inventoryscript start the app, scan the code
  2. Technology and securityagent tech-analyst · script scanners
  3. Roles and workflowsagent workflow-analyst · planner · script user stories
  4. Reviewperson approves requirements, stories and risks
  5. Test designagent test-designer · generator · Xray export
  6. Executescript every tier, clean-up, triage, k6, upgrade
  7. Bugsagent bug-reporter · Jira after confirm
  8. Reportscript coverage, RTM, dashboard

User stories

build-stories turns the requirements into user stories. Code does the grouping, priority and traceability; the workflow-analyst only words the story line and acceptance criteria, and a check re-derives everything else.

  • Keep stories protect today's behaviour.
  • Fix stories hold the intended rule. The as-is behaviour it replaces is listed, never used as an acceptance criterion.
  • Outputs: stories.yaml, docs/07-user-stories.md, and a Jira-ready JSON that is not sent anywhere.

Rules it keeps

  • Every claim cites code; a document that doesn't resolve, or quotes seed data or a secret, is rejected.
  • The target's source is never edited, and tests only touch the local copy. Payment and other outside hosts are blocked.
  • Each test logs in on its own session. A finding counts as confirmed only when a test fails at the assertion that names it.
  • No skipped tests: a test exists only when it can run, and a missing input fails with its reason.
  • Each run cleans up its test data and keeps a full record in output/runs/.
  • Nothing is written to Jira or Xray without a dry run the person confirms.
  • Tests of the plugin: unit, hooks, contract and integration (Docker), plus the agents themselves on a fixture app with planted answers, checked by code. CI runs them on every push.
