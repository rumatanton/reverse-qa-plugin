Claude Code plugin · how it works

reverse-qa

Give it an app with no documentation. It works out how the app is built and used, then writes the requirements, user stories, test cases, a Playwright test framework, test results, findings and bug reports.

The tool is not tied to a stack or to one app: see Works for any app. The parts in detail are on the Architecture page.

The agent at a glance

One fixed recipe drives four subagents, three Playwright agents and 24 skills, a script each. Three hooks run by themselves, and the model cannot skip them: one installs the plugin’s packages when a session starts, one refuses any edit to the target, and one checks every file that is written.

Works for any app

The tool is not tied to a technology. Two parts plug in: a rule pack reads the source, and a driver reaches the running app. Everything else is the same for every app, because it reads files, not a framework.

Pages without a dedicated pack

crawl-app walks the running web app as every role, in a real browser. It is GET navigation only: it never submits a form or clicks a button. It stays inside the app: links to other hosts are recorded, never followed. It leaves alone links that look destructive (logout, delete, remove, cancel, reset and similar words). It cannot know what every link does, so it is meant for a disposable copy. For an API, the OpenAPI spec lists the endpoints. scan-repo merges both with the source scan and flags routes declared in the code that neither one reached.

Checked on a second app

26 tests, 0 failed, 0 skipped, no browser. Run end to end on a Node JSON API with an OpenAPI spec and a token login, kept in the plugin’s tests as a fixture.

Not built yet, and the first crawl

The Appium driver is not built. Its contract is written in templates/DRIVERS.md, so mobile apps, and desktop apps not built with Electron, get no automated tests today. A desktop app built with Electron is driven through its own windows (built 2026-11-11 and run end to end on a fixture app: 6 screens crawled as 3 roles, 13 tests passed). The first crawl of a real web app ran on 2026-11-10, on a PHP shop: 29 of the 33 pages the PHP parser knows (the four it missed are the logout page, skipped on purpose, and three payment pages only a form post reaches), 12 destructive links left alone, and 17 page-and-role cases where the app logged a server error behind a redirect.

How it works

Code does most of the work. A model is called only where judgment is needed, and code checks what it writes. A person approves before any test is written and confirms every write to Jira or Xray.

The workflow

The recipe runs in this order, every time. Nothing is reordered, and a step is left out only where the app’s kind or settings mean it cannot apply; if a step fails, the run stops and reports it.

The guarantees

  • Every claim cites a file and line

    The check-citations hook runs after every write. A document with a citation that does not resolve cannot pass.

  • The target’s source is never edited

    The protect-target hook blocks any edit inside it. The app runs from an image built from a copy.

  • Outside hosts are blocked in tests

    Tests, scanners and load runs touch only the allowed test hosts. Payment gateways and other integrations are stubbed or blocked in every browser test.

  • No skipped tests

    A test exists only when it can run. A missing input fails with its reason.

  • Findings are confirmed by failing tests

    A finding counts as confirmed only when a test fails at the assertion that names it. A product bug is never patched; its test becomes test.fail() with the finding ID.

  • No Jira or Xray write without a confirmed dry run

    publish-xray and publish-bugs show a dry run first. Nothing is created until the person confirms it.
